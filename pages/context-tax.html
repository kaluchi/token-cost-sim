Фиксированный налог

Системный промт летит в каждом вызове целиком. Чем больше итераций — тем больше раз вы за него платите. Одна и та же цель, но разная стоимость из-за квадратичного эффекта и системного налога.

🔍

Главный тезис

Системный промт (определения инструментов, инструкции, правила) — постоянный налог на каждый API-вызов: отправляется целиком в каждом вызове. Два пути к одному и тому же финальному контексту стоят по-разному: мелкие шаги (много итераций, мелкий инкремент) оплачивают системный налог чаще → квадратичный эффект усиливается. Крупные шаги (меньше итераций, крупный инкремент) — дешевле, несмотря на то же финальное состояние.

Интерпретация

Два crossover-а

Линейный crossover — вызов, на котором пользовательские данные в текущем контексте впервые превышают системные токены. Формула: k > (S − P − d) / δ где δ = data + output.

Кумулятивный crossover — вызов, на котором суммарный объём обработанных пользовательских токенов (по всем вызовам) превышает суммарный объём системных. Происходит позже линейного.

Линейный: P + k·δ + d > S → N = k+1 Кумулятивный: Σ user > S·N → N ≈ 2·(S−P)/δ + 1
Почему крупные шаги дешевле
Путь с N₁ вызовами: Σ input ≈ (S+P)·N₁ + δ₁·N₁²/2 Путь с N₂ вызовами: Σ input ≈ (S+P)·N₂ + δ₂·N₂²/2 При одинаковом финальном контексте: N₁·δ₁ ≈ N₂·δ₂ → N₂ < N₁ (крупнее шаг = меньше итераций) → квадратичный член N₂² ≪ N₁² → системный налог S·N₂ < S·N₁

Крупные шаги выигрывают дважды: меньше квадратичного роста данных и меньше системного налога.

Практические рекомендации
  • Инвестируй в промт — подробное описание задачи на старте сокращает число уточняющих итераций
  • Инструменты, возвращающие крупные релевантные блоки за один вызов, дешевле многих мелких запросов
  • Системный промт — фиксированный налог: его нельзя уменьшить, но можно платить его реже (меньше итераций)
  • Prompt Caching снижает и системный налог (~10%), и стоимость повторной передачи данных
  • При длинных сессиях (N > crossover) данные доминируют — фокусируйся на компактности tool results
Техники «крупных шагов» — как уменьшить N

Каждая из этих техник увеличивает объём полезной работы за одну итерацию, сокращая общее число API-вызовов:

Подготовка контекста (↑ начальный промт)

  • CLAUDE.md / project docs — архитектура, конвенции, ключевые пути файлов. Агент не тратит итерации на разведку структуры проекта
  • Детальное ТЗ с acceptance criteria — чем точнее описана задача, тем меньше уточняющих циклов «попробовал → не то → переделал»
  • Контекст в промте, а не в поиске — вставить релевантные сниппеты кода прямо в запрос вместо того, чтобы агент искал их сам через grep/glob

Укрупнение tool results (↑ данных за вызов)

  • Множественные чтения — читать несколько связанных файлов в одном вызове (или параллельные tool calls), а не по одному
  • Grep с широким контекстом — -C 10 или -A 20 вместо точечных попаданий, чтобы избежать повторных чтений «а что вокруг?»
  • git diff + git log — полная картина изменений за один вызов вместо нескольких git status / git show
  • Glob-паттерны — src/**/*.ts для обзора структуры вместо пошагового обхода директорий

Укрупнение записи (↑ output за вызов)

  • Unified diff / мульти-файл эдиты — применить изменения в нескольких файлах одной операцией вместо правок по одному файлу за итерацию
  • Write целого файла — переписать файл целиком, если изменений много, вместо цепочки мелких Edit-ов
  • Микропрограммы / скрипты — написать bash/python-скрипт, выполняющий всю трансформацию за один запуск, вместо ручных пошаговых операций
  • Чейнинг в Bash — cmd1 && cmd2 && cmd3 объединяет несколько операций в один tool call (создание, сборка, тест — за один вызов)

Компонуемость инструментов (↓ итераций за счёт пайплайнов)

  • Bash вместо некомпонуемых MCP-тулов — MCP-инструменты атомарны: один вызов = одна операция = один вызов. Bash-аналоги компонуются через пайпы и редиректы: grep -r "TODO" src/ | wc -l — поиск + подсчёт за один tool call вместо двух
  • head / tail обрезка — cat file.log | tail -100 или head -50 возвращает только нужный фрагмент, а не весь файл; меньше токенов в контексте = дешевле каждый последующий вызов
  • Пайплайн-цепочки — find . -name "*.ts" | xargs grep "deprecated" | sort -u | head -20 — поиск, фильтрация, дедупликация и обрезка за одну итерацию. Через MCP это 3–4 отдельных tool call
  • jq / sed / awk на месте — трансформация данных прямо в shell вместо «прочитал → обработал в output → записал»: jq '.items[] | select(.status=="active")' data.json фильтрует на стороне shell, а не в модели
  • Правило: если MCP-тул делает то же, что одна unix-команда — используй bash-версию, потому что её можно встроить в пайплайн с grep, head, wc, sort и другими бесплатными фильтрами, сокращая и число итераций, и объём данных в контексте

Архитектурные решения

  • Субагенты — делегировать разведку и поиск параллельным агентам, не загрязняя основной контекст
  • Worktree-изоляция — изолированные ветки для экспериментов, чтобы ошибки не порождали итерации отката
  • Compact-стратегия — при приближении к лимиту контекста сжимать историю, а не начинать новую сессию
  • Plan → Execute — сначала составить план (дёшево), потом выполнить за минимум итераций, вместо «проб и ошибок»
